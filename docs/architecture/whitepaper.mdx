# Verglas architecture

## Abstract

Verglas is a Cloudflare-compatible component platform for six products:
Worker, Durable Object, Stream, Pipeline, Sink, and Catalog. Applications are
written against familiar Worker and Durable Object APIs, compiled to WebAssembly
components, and executed by Wasmtime. Durable Object state is ordinary SQL in one
embedded local Turso database per object, stored under the self-hosted cell data
root. The remaining products are Durable Object components with narrow, explicit
responsibilities.

The serving path has three infrastructure processes. `verglas-gateway` accepts
requests and resolves declared bindings. `verglas-celld` supervises isolated
children and enforces lifecycle and resource limits. `verglas-runtime` executes
Worker and Durable Object components, opens each object's local Turso path,
maintains a local Foyer cache, reads the configured S3 origin, and implements a
small set of privileged host capabilities. Infrastructure processes are not
products.

Verglas has no shared Durable Object state layer. Cell filesystem durability is
authoritative for each object's local Turso database. A configured S3-compatible
bucket is the immutable Iceberg origin and the only external dependency in the
current architecture. Foyer's DRAM and NVMe tiers are disposable performance
state.
Iceberg publication is a narrow runtime capability invoked by Catalog; tenants
do not receive raw network, object-store, or catalog credentials.

## 1. Scope

This repository owns:

- the Worker and Durable Object component ABI;
- JavaScript and Python component build pipelines;
- the gateway, celld supervisor, and runtime host;
- Turso-backed Durable Object transactions and lifecycle handling;
- the prebuilt Stream, Pipeline, Sink, and Catalog products;
- local Foyer caching and configured S3 origin access;
- deterministic Parquet and Iceberg commit helpers used by the runtime;
- hermetic acceptance tests and local examples.

Self-hosted operators own deployment orchestration, authentication, cell
placement, and any public `/pipelines/v1` management API. Those surfaces do not
belong in this repository.

This is a prototype. Protocols and on-disk layouts may change between commits.
There are no compatibility aliases, migration layers, fallback implementations,
or retired executables.

## 2. Product model

Exactly six component products exist.

### 2.1 Worker

A Worker is stateless request compute. The gateway instantiates the declared
Worker artifact, supplies only manifest bindings and variables, and dispatches
`fetch`. Worker instances do not receive Durable Object storage. A Worker may
call a declared Durable Object, Stream, Pipeline, Sink, or Catalog binding.

### 2.2 Durable Object

A Durable Object is a named, single-threaded event target. The gateway derives a
stable object identity from the declared namespace and object name. Celld starts
one isolated runtime child for that identity and assigns its local database path
under the self-hosted cell data root. The runtime opens one embedded local Turso
database for durable state.

Every event runs in one SQL transaction. Storage changes, alarms, and Stream
outbox entries commit together. SQL `COMMIT` followed by an explicit WAL
checkpoint is the durability fence. Cell filesystem durability is authoritative
for the DO state. WebSocket effects are withheld until that fence completes. A
failed handler aborts storage and releases no staged effect.

### 2.3 Stream

A Stream accepts append-only records. Each append carries a stable producer,
event, and record identity. The Stream stores the record and deduplication key in
one Turso transaction. Replaying an acknowledged identity returns the existing
position rather than appending a duplicate.

A Stream never transforms records, advances consumer cursors, writes destination
files, or commits tables.

### 2.4 Pipeline

A Pipeline owns transforms, batches, retries, and cursors. It reads ordered
Stream positions, applies the declared SQL transform, freezes deterministic
batches, and delivers each batch to a Sink. It advances its cursor only after
the Sink confirms the same batch identity.

Retry never creates a new batch identity. A Pipeline does not own destination
credentials or catalog state.

### 2.5 Sink

A Sink owns destination policy and delivery idempotency. It validates a frozen
Pipeline batch, derives the deterministic file identity, and calls its declared
Catalog object. A confirmed batch is recorded in the Sink ledger. Reusing a
batch identity with different content is a conflict.

A Sink does not transform records or advance Pipeline cursors.

### 2.6 Catalog

Catalog owns the Iceberg API, immutable deployment configuration, namespace and
table state, and confirmed commit ledger. That state is held in the Catalog
Durable Object's local Turso database under the cell data root. Public catalog
requests terminate at the Catalog product rather than a separate infrastructure
HTTP service.

For an Iceberg data commit, Catalog validates the declared Sink, destination,
batch identity, and expected table state. It then invokes the runtime's private
Iceberg commit capability. The capability can write deterministic objects and
perform the one requested optimistic table update. It cannot select a different
warehouse, expose provider credentials, or provide tenant-controlled network
access. Catalog records a receipt only after the capability confirms the exact
batch and file identity.

## 3. Component contract

All products compile to the `verglas:do` component world named `service`. The
world exposes stateless Worker entry points, stateful Durable Object entry
points, SQL storage, alarms, sockets, and declared binding calls.

The host supplies no command-line arguments, environment variables, filesystem
preopens, clocks beyond declared interfaces, or raw sockets to tenant code.
Standard output and error may be inherited for diagnostics. Components cannot
open object storage or a catalog directly.

Bindings are closed over the deployment manifest. A component can call only a
binding declared for that deployment. Every binding resolves to one of the six
product artifact types or to a reserved, runtime-owned host capability. A host
capability is infrastructure and never appears as a seventh artifact product.

Artifact identity is a lowercase SHA-256 digest. The runtime verifies the
content-addressed component before binding its private event socket. A mismatch,
missing artifact, unknown product, or undeclared binding fails closed.

## 4. Process topology

```text
edge
  |
  v
verglas-gateway
  |
  v
verglas-celld
  |
  v
verglas-runtime
```

`verglas-gateway` owns public ingress, manifest validation, object-name routing,
and long-lived event-socket actors. It does not own Durable Object state or
Iceberg credentials.

`verglas-celld` owns supervision. It creates per-object directories under the
self-hosted cell data root and private Unix sockets, launches runtime children
with local Turso and component configuration, enforces resource ceilings, and
makes a child routable only after its endpoint is ready. Suspension requires a
completed local WAL checkpoint, a drained transactional outbox, and clean
event-endpoint shutdown.

`verglas-runtime` is the only resident execution binary. It embeds Wasmtime,
opens each object's local Turso database, dispatches serialized events, maintains
local Foyer stores, accesses the configured S3 origin, and serves reserved host
capabilities. There is no other serving runtime or binary alias. DO state has no
clustering or replication layer.

Firecracker remains the production isolation boundary. Local process execution
implements the same celld contract for development and hermetic tests.

## 5. Durable Object transactions

At activation, celld gives the runtime the object's local database path under
the self-hosted cell data root. The runtime opens that embedded Turso database
and verifies the component before accepting an event.

For event sequence `E`:

1. the input gate admits exactly one event;
2. the runtime starts one Turso transaction;
3. guest SQL, alarm changes, and Stream sends stage in that transaction;
4. the runtime issues SQL `COMMIT`;
5. the runtime executes an explicit WAL checkpoint;
6. pending Stream outbox rows are delivered idempotently;
7. acknowledged outbox rows are marked delivered;
8. staged socket effects and the terminal response are released.

The `COMMIT` plus explicit WAL checkpoint is the durability fence. A crash before
`COMMIT` leaves no transaction. A crash after `COMMIT` but before the checkpoint
releases no staged effect. A crash after the checkpoint but before Stream
acknowledgement leaves a durable outbox row. A crash after Stream acknowledgement
but before the delivered mark causes an idempotent resend. Activation drains
pending rows before admitting the next tenant event.

Cold restart reopens the same object identity and the same local database path,
verifies the artifact again, drains pending work, and resumes at the committed
state. Cell filesystem durability is authoritative for DO state. No custom SQL
pager, alternate mutation format, local archive, or alternate storage path is
part of this path.

## 6. Local cache and configured S3 origin access

Foyer provides two bounded local tiers:

- DRAM for the hottest blocks and mappings;
- NVMe for a larger restart-recoverable working set.

Both tiers are caches. Missing, evicted, corrupt, or machine-lost entries refill
from the configured S3 origin. A cache admission never acknowledges a durable
mutation and never determines Catalog or Durable Object state.

Object reads are keyed by storage binding, bucket, key, object version, block
geometry, and block index. A response commits to one object version before
streaming, so it cannot combine bytes from different versions. Concurrent fills
for the same key coalesce locally. Hard DRAM, NVMe, fill, and concurrency budgets
bound resource use.

Whole-object and ranged reads use the deployment's host-owned credentials for
the configured S3 origin. Those credentials are not placed in component variables
or WASI state. Customer
bindings preserve the customer's object layout. Managed bindings may use a
Verglas-owned layout only when every read of that binding routes through the
managed service.

The cache is local acceleration only and has no authority over durable state.
Machine loss affects warmth, not correctness; missing entries refill from the
configured S3 origin.

## 7. Iceberg commit capability

The runtime capability accepts one bounded request from the declared Catalog
binding. The request fixes:

- Catalog and Sink identity;
- warehouse, namespace, and table;
- deterministic batch and file identity;
- payload digest and row count;
- compression and bounded records;
- the expected Catalog state used for optimistic publication.

The runtime validates the request against deployment configuration and writes
the deterministic Parquet and Iceberg metadata objects. It returns the proposed
metadata location and complete metadata but never retains or advances a Catalog
head. Reusing one deterministic file identity with different content is an
error; unreferenced immutable objects remain invisible.

The Catalog object validates that proposal, then atomically installs the new
table pointer and commit receipt in Turso/SQLite. Only that transaction makes
the update visible to REST clients or acknowledges Sink. A retry after a lost
runtime response may reproduce an immutable proposal, while a retry after the
SQLite transaction is a pure ledger replay.

The capability is not a general object-store API, ingest service, compactor,
retention service, or Catalog REST server.

Exactly-once behavior is composed from deterministic identities and durable
ledgers:

- Stream deduplicates producer event records;
- Pipeline freezes batches and advances cursors after Sink acknowledgement;
- Sink deduplicates destination delivery;
- Catalog deduplicates Iceberg publication;
- the runtime capability recognizes an already-published deterministic file.

## 8. Failure and lifecycle behavior

The design prefers a slow correct path over an incorrect fast path.

- A cache miss reads the configured S3 origin.
- If the configured S3 origin is unavailable, the operation fails; stale bytes are not substituted.
- A Turso `COMMIT` or WAL checkpoint failure keeps the object behind its durability fence.
- A Stream delivery failure keeps the outbox row and withholds event effects.
- A Sink or Catalog conflict preserves the Pipeline cursor for retry or operator
  resolution.
- A runtime crash is recovered by celld under the same object identity.
- A corrupt or mismatched component never binds the event socket.

Scale-to-zero is a supervision operation, not a storage transfer protocol.
Celld stops admitting events, waits for the transaction and outbox fences,
performs the final Turso `COMMIT` and explicit WAL checkpoint, closes the event
endpoint, and stops the child. The same local database path is reopened on cold
restart. Foyer contents may be retained for faster restart or discarded freely.

## 9. Security and isolation

The gateway validates all public routes and deployment bindings. Celld validates
all launch fields and creates private per-object paths. The runtime verifies
artifact digests and grants only the imports required by the component world.

Tenant components receive no provider credentials, host filesystem path, raw
network capability, or unrestricted subprocess capability. Cross-object and
host-service calls carry the declared binding identity. The target validates the
stable object, Sink, Catalog, and destination identities again before mutation.

Resource budgets are hard ceilings. Wasmtime fuel or epoch limits, process CPU
and memory limits, Turso event serialization, cache capacities, request body
limits, batch row limits, and concurrency limits for the configured S3 origin are
enforced at their respective boundaries.

## 10. Verification

Acceptance is based on observable behavior rather than type-level substitutes.
The repository verifies:

- JavaScript and Python component builds with no ambient WASI capability;
- real gateway → celld → runtime request execution;
- SQL commit and rollback through Turso;
- commit-gated WebSocket effects;
- kill-point recovery of the transactional Stream outbox;
- deterministic Stream, Pipeline, Sink, and Catalog replay;
- Foyer DRAM/NVMe hits and configured S3 origin refill after local loss;
- Iceberg file and snapshot identity across retry;
- cold restart of the complete six-product chain;
- static absence of retired binaries, crates, protocol fields, and products.

The final recorded transcript must contain the commands and outputs from a real
JavaScript and Python cold-restart run. Documentation is not accepted as proof
when the corresponding executable path was not exercised.

## 11. Deliberate non-goals

Verglas does not implement a custom Durable Object SQL implementation, an
alternate mutation or storage protocol, a direct Durable Object lakehouse offload path, a
background job Worker, or a public Pipelines control plane. Catalog is a
product, not a separate infrastructure service.

Streams append. Pipelines transform and checkpoint. Sinks deliver idempotently.
Catalog owns API and table state. Cell filesystem durability owns Durable Object
state, and the configured S3-compatible bucket owns immutable Iceberg objects.
Foyer is disposable acceleration.
These boundaries are the architecture.
