The Durable Object (DO) is one of the six products. It is a named Worker class
with strictly serialized events and one embedded Turso `0.7.2` database. A
Worker reaches it through an environment binding; a DO is never a public
standalone route. This page describes the target contract and does not claim
that the hosted product is shipped before PP2 and its evidence pass.

The local Turso database is a working copy. Turso's ordinary WAL is used for
local transactions, and the cloud provisions one distinct remote Turso
database, URL, and token for each DO. `push()` sends committed state through an
external sync ingress. That ingress validates the current placement lease before
forwarding the push. The lease fences stale owners; it does not add a second SQL
commit authority or turn object storage into the DO database.

## State and event boundary

A DO owns only its per-object application state and platform state:

- byte key/value storage;
- SQLite-compatible SQL tables and DDL/DML;
- one durable alarm;
- WebSocket attachments; and
- an optional transactional outbox for a bound Stream.

Reserved Turso tables hold the platform rows. Tenant SQL runs in the same
Turso transaction as the event. Reads observe the event snapshot plus its own
staged writes. A successful event requires the local transaction commit and
remote `push()` confirmation. Socket effects and other gated effects are
released only after that boundary.

```js
export class Counter extends DurableObject {
  async fetch(request) {
    await this.ctx.storage.sql.exec(
      "CREATE TABLE IF NOT EXISTS counters (value INTEGER NOT NULL)"
    );
    await this.ctx.storage.sql.exec(
      "INSERT INTO counters (value) VALUES (1)"
    );
    return Response.json(
      await this.ctx.storage.sql.exec("SELECT value FROM counters")
    );
  }
}
```

The target WIT boundary returns rows as JSON-compatible records. Alternate
mutation envelopes are not part of the DO transaction protocol. There is no
custom SQLite pager, secondary state store, or alternate DO table provider. A
Pipeline's stateless SQL evaluator is separate from DO storage and commits.

## Transactional Stream publication

A DO may bind one or more Streams. Direct publication uses the binding:

```js
await env.STREAM.send(records);
```

For selected SQL tables, a transactional outbox couples committed state to
publication without coupling the DO to Stream storage. For event sequence `E`,
the same Turso transaction writes rows identified by
`(object-id, E, record-index)`. After the transaction and remote push are
durable, the host sends pending rows to the Stream. The Stream assigns its
strictly increasing sequence and deduplicates the producer identity.

Only confirmed Stream ingestion lets the host mark a row delivered. A crash
after ingestion and before that mark resends the same identity; Stream dedup
makes the resend harmless. A crash before ingestion leaves a pending row. The
host drains pending rows before admitting another event when publication is
required. Stream unavailability applies backpressure rather than silently
dropping a committed record.

## What the DO does not own

The six-product boundary prevents an ordinary DO from becoming a hidden
lakehouse:

- **Pipeline** is a prebuilt Worker/DO that owns its Stream cursor, stateless
  SQL transform, batching, and retry state. It contains no destination-specific
  Iceberg code.
- **Sink** is a prebuilt Worker/DO that owns idempotent delivery. The first Sink
  writes Parquet and commits Iceberg snapshots through a Catalog binding.
- **Catalog** is a prebuilt Worker/DO that owns Iceberg REST, namespace/table
  state, and the commit ledger in Turso. Its narrow runtime capability owns the
  Iceberg and object-storage libraries.
- **Cache** remains independent runtime acceleration and routing infrastructure.

A customer binding remains usable without Verglas. A managed binding keeps its
Verglas-owned object layout and read path. Neither rule gives a DO a direct
Iceberg offload path; Sink and Catalog own those operations.

## Placement and recovery

Each active DO can run in an isolated process or microVM selected by the
platform. The executor serializes events for one object and uses the DO's own
remote Turso database for recovery. A lifecycle supervisor may suspend an
inactive object only after required pushes and Stream outbox publication are
complete. A takeover revokes the old sync owner before the replacement opens
the database.

Worker execution is stateless and pool-executed. Stream, Pipeline, Sink, and
Catalog are separate prebuilt Worker/DO deployments, not hidden modes of a DO.
See [DO Workers](/docs/architecture/do-workers), [cell
deployment](/docs/architecture/cells), and the [normative platform
page](/docs/architecture/primitives-platform) for the component and lifecycle
criteria.
