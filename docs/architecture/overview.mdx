Verglas has exactly six products: **Worker**, **Durable Object**, **Stream**,
**Pipeline**, **Sink**, and **Catalog**. Worker is the stateless primitive. DO
is the stateful primitive, backed by one embedded local Turso `0.7.2` database
under the self-hosted cell data root. Stream, Pipeline, Sink, and Catalog are
prebuilt Worker/DO deployments with separate ownership boundaries.
See the [normative platform page](/docs/architecture/primitives-platform) for
PP1–PP10.

The platform also contains independent infrastructure. A storage binding is
either customer-owned or managed. Against a customer binding, the object store
and Iceberg catalog remain authoritative and Verglas accelerates access to them.
Against a managed binding, Verglas owns the object layout, serves every read,
and is the authority for acknowledged cache state until it drains to the
origin.

```mermaid
flowchart LR
    U["HTTP / bindings"] --> W["Worker\nstateless"]
    W --> D["Durable Object\nlocal Turso 0.7.2"]
    W --> S["Stream\nordered JSON"]
    S --> P["Pipeline\nSQL + batch + retry"]
    P --> K["Sink\nidempotent delivery"]
    K --> C["Catalog\nIceberg REST"]
    R["verglas-runtime"] --> O["S3-compatible bucket\nimmutable Iceberg origin"]
    R --> C
```

The serving topology is `edge → verglas-gateway → verglas-celld →
verglas-runtime`. The cell filesystem is authoritative for local Durable Object
state. There is no clustering or replication layer. The configured
S3-compatible bucket is the immutable Iceberg origin, and Foyer contents are
disposable.

## Repository boundary

| Repository | Responsibility |
| --- | --- |
| `verglas` | Public Worker/Durable Object runtime, local Turso/Foyer adapters, Iceberg/Catalog capabilities, clients, documentation, and product contracts. |
| Self-hosted deployment | Edge ingress, gateway, celld placement and lifecycle, runtime execution, and operator management. |
| `verglas-app` | Optional operator console and workspace client. |

The public repository does not add a hidden job runtime, queue service, custom
DO database, or direct DO-to-Iceberg path. Self-hosted operators consume explicit
public contracts. Product implementations that are not yet accepted are
documented as Target or Gap rather than as shipped features.

## Product and infrastructure roles

| Role | Responsibility |
| --- | --- |
| Worker | Stateless ingress and binding calls. |
| Durable Object | Serialized per-object state in its local Turso database, including KV, SQL, alarms, attachments, and optional Stream outbox rows. SQL `COMMIT` plus an explicit WAL checkpoint fences state on the cell filesystem. |
| Stream | Ordered durable JSON records and producer-identity deduplication; no offload or consumer offsets. |
| Pipeline | Stream cursor, stateless SQL transform, batching, retry, and Sink confirmation. |
| Sink | Idempotent delivery; first adapter writes Parquet and commits Iceberg through Catalog. |
| Catalog | Iceberg REST and metadata commits using the existing catalog and S3-compatible object-storage libraries. |
| Runtime | Wasmtime component execution, local Turso Durable Object state, Foyer cache tiers, configured S3 origin access, and narrow privileged capabilities. |

## Standing requirements

- A customer binding stays readable through its original catalog and bucket.
- A managed binding is left through an explicit detach that drains acknowledged
  state to the origin.
- Object version participates in cache identity, so stale paths cannot return
  bytes from another generation.
- DRAM, NVMe, CPU, concurrency, and background work obey hard ceilings.
- A DO never receives raw object-store or catalog credentials; Sink and Catalog
  use explicit narrow bindings for privileged operations.
