This page describes the target placement shape for a stateful Durable Object.
It does not describe a separate database product or a shipped scheduler.
The [Worker primitives platform](/docs/architecture/primitives-platform) defines
the six products and PP1–PP10 acceptance criteria.

A cell runs one active DO event executor in one isolated environment. The DO
owns one embedded local Turso `0.7.2` database under the self-hosted cell data
root. Turso's ordinary WAL carries the local transaction, and SQL `COMMIT` plus
an explicit WAL checkpoint is the durability fence. Cell filesystem durability
is authoritative for DO state. There is no clustering or replication layer.

```text
isolated cell
└── DO event executor
    ├── one stateful Worker class
    │   └── tenant WASM component (verglas:do-worker world)
    ├── local Turso 0.7.2 WAL database under the cell data root
    ├── optional transactional Stream outbox
    └── private event endpoint
```

The tenant component is fetched by content digest and verified before
instantiation. CPU, memory, and local disk budgets are hard ceilings. Compiled
Worker code may be cached outside a cell, but mutable DO state and execution do
not share a process with another tenant payload.

## Turso durability fence

A DO event runs inside one local Turso transaction. The host acknowledges the
event only after SQL `COMMIT` succeeds and the runtime completes an explicit WAL
checkpoint. The cell filesystem is the authoritative durability boundary for the
DO database.

Celld assigns one local data path to each object beneath the self-hosted cell
data root. Cold restart reopens that same path and resumes from its committed
state. A path is never shared between DO identities. The runtime retains no
custom SQLite pager, alternate SQL provider, or direct Iceberg offload path.
DO state has no clustering or replication layer.

## Optional Stream outbox

A DO may publish selected committed SQL changes to a bound Stream. The Turso
transaction writes deterministic outbox rows identified by
`(object-id, event-sequence, record-index)`. After the Turso durability boundary,
the host sends pending rows to the Stream. The Stream deduplicates those
identities; only then does the host mark rows delivered and release any effect
that is gated on publication.

A crash after Stream ingestion but before the delivered mark causes an
idempotent resend. A crash before ingestion leaves a durable pending row. The
host drains pending rows before admitting the next event when publication is
required. Stream unavailability applies backpressure rather than losing a
committed record.

## Scale-to-zero

The lifecycle supervisor may suspend an inactive DO after its local Turso
transaction has committed, the explicit WAL checkpoint has completed, and no
gated publication is pending. The local database remains at its assigned path;
Foyer contents may be discarded.

```text
fence new events
      ↓
drain required Stream outbox rows
      ↓
commit and checkpoint the final local Turso transaction
      ↓
suspend the isolated DO environment
      ↓
next request reopens the same local database path
      ↓
release the triggering event after the local durability fence
```

Foyer is disposable cache acceleration. The configured S3-compatible bucket is
the immutable Iceberg origin. Sink delivery and Catalog publication remain
separate from ordinary Durable Object state; a DO does not materialize its
database directly to Iceberg.
