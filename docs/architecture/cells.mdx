This page describes the target placement shape for a stateful Durable Object.
It does not describe a separate database product or a shipped hosted scheduler.
The [Worker primitives platform](/docs/architecture/primitives-platform) defines
the six products and PP1–PP10 acceptance criteria.

A cell runs one active DO event executor in one isolated environment. The DO
owns one embedded Turso `0.7.2` database and its sync sidecars. Turso's ordinary
WAL is the local durability path; one remote Turso database per DO is the
machine-loss recovery source.

```text
isolated cell
└── DO event executor
    ├── one stateful Worker class
    │   └── tenant WASM component (verglas:do-worker world)
    ├── Turso 0.7.2 WAL database and sync sidecars
    ├── optional transactional Stream outbox
    └── private event endpoint
```

The tenant component is fetched by content digest and verified before
instantiation. CPU, memory, and local disk budgets are hard ceilings. Compiled
Worker code may be cached outside a cell, but mutable DO state and execution do
not share a process with another tenant payload.

## Turso durability and sync fencing

A DO event runs inside one Turso transaction. The host acknowledges the event
only after the transaction commits locally and `push()` confirms the remote sync
boundary. The cloud provisions a distinct remote URL and token for every DO.
An external sync ingress validates the current placement lease before forwarding
the push, so a stale cell cannot open or push another owner's database.

The lease is a placement and synchronization fence. It is not a lease-fenced
object-store write path, a second SQL commit authority, or a custom database
protocol. The DO runtime retains no custom SQLite pager, alternate SQL provider,
or direct Iceberg offload path.

A replacement cell first revokes the prior owner, opens the DO's own remote
Turso database, and restores a local working copy with its sync sidecars. A
local directory must never be copied between DO identities because it carries
the persisted Turso sync-client identity.

## Optional Stream outbox

A DO may publish selected committed SQL changes to a bound Stream. The Turso
transaction writes deterministic outbox rows identified by
`(object-id, event-sequence, record-index)`. After the Turso durability boundary,
the host sends pending rows to the Stream. The Stream deduplicates those
identities; only then does the host mark rows delivered and release any effect
that is gated on publication.

A crash after Stream ingestion but before the delivered mark causes an
idempotent resend. A crash before ingestion leaves a durable pending row. The
host drains pending rows before admitting the next event when publication is
required. Stream unavailability applies backpressure rather than losing a
committed record.

## Scale-to-zero

The lifecycle supervisor may suspend an inactive DO after its local sync client
has pushed through the required durability boundary and no gated publication is
pending. The remote Turso database remains the recovery source; retaining a
local working copy only shortens restore.

```text
fence new events
      ↓
drain required Stream outbox rows
      ↓
commit and push the final Turso transaction
      ↓
suspend the isolated DO environment
      ↓
next request provisions an owner with a valid placement lease
      ↓
open the DO's remote database and restore its local working copy
      ↓
release the triggering event after the sync boundary
```

Cache acceleration, Sink delivery, and Catalog publication remain separate
from ordinary Durable Object state. A DO does not materialize its database
directly to Iceberg; Sink and Catalog own that path.
