This page describes the target execution shape for the Worker and Durable
Object primitives. The [Worker primitives platform](/docs/architecture/primitives-platform)
is normative and its PP1–PP10 criteria are frozen. The component and lifecycle
work is not claimed as shipped until its acceptance evidence exists.

A **Worker** is the stateless primitive: a pool-executed `fetch` handler with no
identity and no storage. A **Durable Object** is a named, stateful Worker class
reached only through bindings (`env.NS.idFromName` → `get` → stub `fetch`). A DO
runs strictly serialized events against one embedded local Turso `0.7.2`
database under the self-hosted cell data root. The cell filesystem is
authoritative for that database; DO state has no clustering or replication.

```text
gateway (owns HTTP + WebSocket connections)
       │  public request → stateless Worker
       ▼
Worker ── env bindings ──┬── Durable Object
                         │      ├── local Turso 0.7.2 WAL database
                         │      ├── transactional outbox (optional Stream)
                         │      └── private event endpoint
                         ├── Stream
                         ├── Pipeline
                         ├── Sink
                         └── Catalog
```

The DO runtime has no custom SQLite pager, alternate SQL provider, mutation
envelope, direct Iceberg offloader, or vector/graph mutation domain. A
Pipeline's stateless SQL evaluator is separate from DO storage.

## The ABI

The component targets the `verglas:do-worker` WIT world. The exact ABI remains a
component contract; the following surfaces describe its target behavior:

- **Exports** are the lifecycle and event surface: `init` runs once per
  component instantiation before the first event; `fetch` handles routed HTTP
  requests, `alarm` handles the DO's durable alarm, and `websocket-message`
  and `websocket-close` handle accepted connections.
- **`storage` imports** — `get`, `put`, `delete`, `list`, `sql`, and alarm
  verbs — are host functions bound to the embedded local Turso database. A
  storage call is local to the event executor, never a call to a separate SQL
  service. Reads see the event's Turso snapshot plus its own staged writes. A
  successful event requires SQL `COMMIT` followed by an explicit WAL checkpoint.
- **`sockets` imports** — `send`, `close`, `set-attachment`, `get-attachment`,
  and `attached` — stage effects against connections the gateway holds.
  Attachments are bounded at 16 KiB and persist in DO state.

Reserved Turso tables hold byte KV, the single alarm, WebSocket attachments,
event sequencing, and optional Stream outbox rows. Tenant SQL uses the same
Turso transaction and the SQLite-compatible DDL/DML surface. The host exposes
rows through the WIT JSON-row boundary; no alternate mutation envelope is part
of DO commit or publication.

## Event execution: one at a time, gated

Events execute strictly serialized per DO. The host admits one event, runs the
handler to completion, issues SQL `COMMIT`, and executes an explicit WAL
checkpoint before releasing the event result or any gated socket effects.

- **Input gate.** No second event observes state between another event's start
  and its Turso commit. Concurrent arrivals wait.
- **Output gate.** Outbound socket sends staged during an event are released
  only after the local Turso `COMMIT` and explicit WAL checkpoint complete. An
  aborted or incomplete event releases nothing.
- **Publication gate.** If the DO has a Stream binding, selected committed
  changes first become deterministic outbox rows. The host sends those rows to
  the Stream, which deduplicates `(object-id, event-sequence, record-index)`.
  A crash after Stream confirmation but before marking a row delivered causes
  an idempotent resend, not a duplicate record or a gap.

A handler failure does not roll back a transaction that already reached the
cell filesystem durability fence. Stream unavailability applies backpressure to
a streaming-enabled DO rather than dropping committed records.

## Code artifacts

A deployment artifact is a content-addressed immutable object. The host fetches
it by digest, verifies SHA-256 before instantiation, and fails closed on a
mismatch. Compiled AOT artifacts may be cached outside the isolation boundary
keyed by the same digest; a cache is only an acceleration. Pre-initialization
and machine suspend/resume are lifecycle optimizations, not storage authority.

## Languages

Any language with component tooling can target the world — Rust via
`cargo component`, Go via TinyGo, and Python via componentize-py. JavaScript and
TypeScript are bundled into the component with ComponentizeJS and
StarlingMonkey. The platform runs components, not language runtimes: language
support is a build-time property of the artifact.

## Connections live in the gateway, not the guest

HTTP and WebSocket connections terminate at the platform ingress, never inside
the component. The gateway:

1. resolves a name to a DO id and wakes the target on demand;
2. holds WebSockets while the DO is suspended;
3. answers configured auto-responses without waking the DO;
4. delivers serialized events and releases commit-gated sends to the right
   connections; and
5. reads per-connection attachments from DO state on wake so a rehydrated
   Worker can rebuild its session map.

Because attachments and the alarm are committed local Turso state, a DO that
hibernates or cold-restarts reopens its existing path and rebuilds the context
described by its last durable transaction.

## Alarms

`set-alarm` writes the DO's single alarm row inside the current Turso
transaction. After `COMMIT` and the explicit WAL checkpoint complete, the
supervisor arms a wake at the deadline; firing delivers one `alarm` event with
the scheduled time. The alarm survives hibernation and cold restart because it
is ordinary committed state; the timer is derived, never authoritative.

## Placement substrate

The self-hosted cell lifecycle supervisor creates one isolated execution
environment per active DO. Local process execution supports development and
tests; a microVM provides production isolation. Verglasd assigns each DO's local
Turso database under the self-hosted cell data root and reopens that same path
on cold restart. The cell filesystem remains authoritative for state.

Worker execution remains stateless and pool-executed. Stream, Pipeline, Sink,
and Catalog are prebuilt Worker/DO deployments with their own ownership
boundaries; they are not hidden runtimes inside a tenant DO.
