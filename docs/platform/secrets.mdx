A Verglas secret is encrypted credential material plus public metadata: a
stable ID, provider type, URI scope, and version. Database records store the
secret ID, not its value.

## Before you begin

Set the tenant access endpoint and its local control credential:

```bash
export VERGLAS_ACCESS_ENDPOINT=http://127.0.0.1:8345
export VERGLAS_TOKEN=verglas-local-access
```

Do not put a secret value in a command argument. Pipe it to `verglas secret
create`, or run the command interactively and enter the value at the hidden
prompt.

## Create an S3 secret

Use a scope no broader than the object prefix the workload needs:

```bash
jq -nc \
  --arg accessKeyId "$AWS_ACCESS_KEY_ID" \
  --arg secretAccessKey "$AWS_SECRET_ACCESS_KEY" \
  --arg sessionToken "${AWS_SESSION_TOKEN:-}" \
  --arg region "${AWS_REGION:-us-west-2}" \
  '{accessKeyId, secretAccessKey, sessionToken, region}' \
| verglas secret create customer_s3 \
    --type s3 \
    --scope s3://customer-bucket/finance
```

The CLI prints only `created secret customer_s3`. It never echoes the value.

## Create an Iceberg REST secret

For a bearer-authenticated catalog, pipe the bearer token as the secret value:

```bash
printf '%s' "$ICEBERG_CATALOG_TOKEN" \
| verglas secret create customer_catalog \
    --type iceberg-rest \
    --scope https://catalog.example.com/iceberg
```

For a SigV4 catalog such as Amazon S3 Tables, use the structured AWS value shown
in [Declare an AWS lakehouse](/docs/platform/databases#declare-an-aws-s3-and-s3-tables-lakehouse).

## Inspect metadata

List secret metadata through the access API:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer $VERGLAS_TOKEN" \
  "$VERGLAS_ACCESS_ENDPOINT/v1/secrets" \
| jq 'map({id, kind, scope, current_version})'
```

The response never contains plaintext or ciphertext.

## How scope resolution works

Verglas canonicalizes URI scopes and selects the longest authorized match. For
example, `s3://customer-bucket/finance` is more specific than
`s3://customer-bucket`. Equal-specificity ambiguity fails closed.

The calling principal must have `use_secret` on the selected secret resource.
Only the trusted runtime-resolution endpoint can decrypt a value. Applications,
Jobs, Integrations, and agent turns receive a capability or an injected binding,
not raw tenant credentials.

## Rotate a secret

Rotation preserves the stable resource ID and scope while incrementing the
version:

```bash
jq -nc \
  --arg principal_id local-admin \
  --arg value "$NEW_CATALOG_TOKEN" \
  '{principal_id, value}' \
| curl --fail-with-body \
    --request PUT \
    --header "Authorization: Bearer $VERGLAS_TOKEN" \
    --header 'Content-Type: application/json' \
    --data-binary @- \
    "$VERGLAS_ACCESS_ENDPOINT/v1/secrets/customer_catalog"
```

Existing database bindings continue to reference `customer_catalog`; a newer
overlapping secret cannot silently rebind them.

<Note>
The current access API does not expose secret deletion. Rotate a compromised
value immediately, remove every dependent resource, and follow the deployment's
administrative retention process. A delete API must remove both encrypted
versions and the authorization resource atomically before it is documented as a
supported operation.
</Note>
