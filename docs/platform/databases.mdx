A database is a named tenant resource. Each database has its own runtime and
credential bindings. A lakehouse combines object storage with an Iceberg REST
catalog. A Postgres database uses a managed Verglas Neon runtime.

## Choose a database configuration

| Type | Object storage | Catalog | Current OSS support |
| --- | --- | --- | --- |
| Managed lakehouse | Deployment R2 bucket | Tenant Lakekeeper | Available |
| External lakehouse | Scoped S3 URI | Iceberg REST catalog over that storage | Declaration preview |
| Catalog-owned lakehouse | S3 Tables or R2 Data Catalog | Provider Iceberg REST endpoint | Not yet representable |
| Postgres | Managed Neon storage | Postgres catalog | Available |

<Warning>
The current OSS data runtime activates managed lakehouses and managed Postgres
databases. It validates external S3 and Iceberg REST declarations and resolves
their stable secret IDs, but then fails closed with
`requires a scoped external runtime binding that is not active`. Do not use an
external declaration for production data until that runtime binding ships.
</Warning>

## Create a managed lakehouse

Before you begin, [start the OSS stack](/docs/get-started/self-host) and export
the local endpoints:

```bash
export VERGLAS_ENDPOINT=http://127.0.0.1:8334
export VERGLAS_ACCESS_ENDPOINT=http://127.0.0.1:8345
export VERGLAS_TOKEN=verglas-local-access
```

Create a lakehouse named `analytics`:

```bash
verglas db create analytics --type lakehouse --json
```

The response identifies both managed components:

```json
{
  "type": "lakehouse",
  "name": "analytics",
  "storage": { "mode": "managed" },
  "catalog": { "mode": "managed-lakekeeper" }
}
```

Verglas creates a warehouse in the tenant Lakekeeper service. The deployment's
R2 bucket remains the durable object store; the named database does not receive
the deployment credential.

Verify that the query runtime can open the database:

```bash
verglas query analytics 'SELECT 1 AS ready' --json
```

Expected result:

```json
{
  "columns": ["ready"],
  "rows": [{ "ready": 1 }],
  "row_count": 1
}
```

## Create a Postgres database

Create an independent database on the managed Verglas Neon runtime:

```bash
verglas db create operational --type postgres --json
```

The database resource becomes available only after the runtime passes an
authenticated SQL probe. Lakehouse query routes reject Postgres database names;
use the Postgres connection contract exposed by the database runtime.

## Validate Cloudflare R2 Data Catalog

R2 Data Catalog is another catalog-owned-storage service: the catalog and table
data belong to one R2 bucket. Use a provisioning token to create the resource;
do not save an account-wide administrative token as a runtime secret.

```bash
export CLOUDFLARE_ACCOUNT_ID=YOUR_ACCOUNT_ID
export CLOUDFLARE_API_TOKEN=YOUR_PROVISIONING_TOKEN
export R2_CATALOG_BUCKET=YOUR_UNIQUE_BUCKET

curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --header 'Content-Type: application/json' \
  --data "{\"name\":\"$R2_CATALOG_BUCKET\"}" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/r2/buckets"

curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/r2-catalog/$R2_CATALOG_BUCKET/enable"
```

Wait until the catalog reports `active`:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/r2-catalog/$R2_CATALOG_BUCKET" \
| jq '.result | {name, status, credential_status}'
```

The Iceberg REST endpoint has this form:

```text
https://catalog.cloudflarestorage.com/ACCOUNT_ID/BUCKET
```

Like S3 Tables, R2 Data Catalog cannot be paired with a separate
`--data-path`. The current database request does not yet represent this storage
mode.

## Validate AWS S3 and S3 Tables

This example validates both AWS services used in an external deployment. They
are separate storage models:

- A general-purpose S3 bucket can hold an Iceberg warehouse managed by an
  external catalog such as Lakekeeper.
- An S3 Tables table bucket owns both its optimized table storage and its
  Iceberg REST catalog. It does not catalog data files in the general-purpose
  bucket.

The AWS profile must be able to manage both services.

Set example names and create both buckets:

```bash
export AWS_PROFILE=YOUR_AWS_PROFILE
export AWS_REGION=us-west-2
export S3_BUCKET=YOUR_GLOBALLY_UNIQUE_BUCKET
export TABLE_BUCKET=YOUR_TABLE_BUCKET

aws s3api create-bucket \
  --bucket "$S3_BUCKET" \
  --region "$AWS_REGION" \
  --create-bucket-configuration LocationConstraint="$AWS_REGION"

aws s3api put-public-access-block \
  --bucket "$S3_BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

TABLE_BUCKET_ARN=$(aws s3tables create-table-bucket \
  --region "$AWS_REGION" \
  --name "$TABLE_BUCKET" \
  --query arn \
  --output text)
```

Create a namespace to verify the external catalog:

```bash
aws s3tables create-namespace \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN" \
  --namespace docs_example

aws s3tables list-namespaces \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN"
```

Create a table to verify catalog and table-storage access:

```bash
aws s3tables create-table \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN" \
  --namespace docs_example \
  --name events \
  --format ICEBERG \
  --metadata '{
    "iceberg": {
      "schema": {
        "fields": [
          {"name":"event_id","type":"string","required":true},
          {"name":"observed_at","type":"timestamp","required":true}
        ]
      }
    }
  }'

aws s3tables get-table \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN" \
  --namespace docs_example \
  --name events
```

Amazon S3 Tables exposes Iceberg REST at
`https://s3tables.REGION.amazonaws.com/iceberg`. It uses AWS Signature Version
4 with the service name `s3tables`; the table bucket ARN is the warehouse.

Save one secret for each provider scope. Secret values are read from standard
input so they do not appear in shell history or the process list:

```bash
aws configure export-credentials \
  --profile "$AWS_PROFILE" \
  --format process \
| jq -c '{
    accessKeyId: .AccessKeyId,
    secretAccessKey: .SecretAccessKey,
    sessionToken: .SessionToken,
    region: env.AWS_REGION
  }' \
| verglas secret create aws_s3 \
    --type s3 \
    --scope "s3://$S3_BUCKET"

aws configure export-credentials \
  --profile "$AWS_PROFILE" \
  --format process \
| jq -c '{
    accessKeyId: .AccessKeyId,
    secretAccessKey: .SecretAccessKey,
    sessionToken: .SessionToken,
    region: env.AWS_REGION,
    signingName: "s3tables"
  }' \
| verglas secret create aws_s3tables \
    --type iceberg-rest \
    --scope "https://s3tables.$AWS_REGION.amazonaws.com/iceberg"
```

### Current binding limitation

Do not combine `s3://$S3_BUCKET` with the S3 Tables endpoint in one database
declaration. S3 Tables owns its table storage. The current Verglas request
requires `--data-path` for every external catalog, so it cannot yet express this
catalog-owned-storage model. General-purpose S3 plus an external catalog over
that same S3 prefix is accepted as a declaration, but activation returns HTTP
`502` until the scoped external runtime binding ships. Verglas removes the
failed database declaration; encrypted secrets remain available for a later
retry.

## Connect with SQL

The OSS server exposes SQL over HTTP rather than a PostgreSQL wire endpoint for
lakehouses.

Use the CLI:

```bash
verglas query analytics \
  'SELECT namespace_name, table_name FROM information_schema.tables LIMIT 25' \
  --json
```

Or call the database-scoped route directly:

```bash
curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer $VERGLAS_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"sql":"SELECT 1 AS ready"}' \
  "$VERGLAS_ENDPOINT/v1/databases/analytics/query"
```

Each request selects one database explicitly. A query cannot fall through to a
process-wide default catalog.

## Connect with the TypeScript SDK

Install `@verglas/sdk`, then connect the admin client to the data endpoint:

```ts
import { connectAdmin } from "@verglas/sdk";

const verglas = connectAdmin({
  endpoint: process.env.VERGLAS_ENDPOINT!,
  token: process.env.VERGLAS_TOKEN!,
});

const result = await verglas.query(
  "analytics",
  "SELECT 42 AS sdk_ready",
);

console.log(result.rows);
// [{ sdk_ready: 42 }]
```

Use `connectAdmin` for database-scoped SQL and catalog operations. Worker code
receives an already connected `ctx.client`; it must not construct a second
client or receive deployment credentials.

## Delete test resources

Delete a Verglas database through the access API:

```bash
curl --fail-with-body \
  --request DELETE \
  --header "Authorization: Bearer $VERGLAS_TOKEN" \
  "$VERGLAS_ACCESS_ENDPOINT/v1/databases/analytics"
```

Delete the AWS catalog test resources before deleting their buckets:

```bash
aws s3tables delete-table \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN" \
  --namespace docs_example \
  --name events

aws s3tables delete-namespace \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN" \
  --namespace docs_example

aws s3tables delete-table-bucket \
  --region "$AWS_REGION" \
  --table-bucket-arn "$TABLE_BUCKET_ARN"

aws s3 rm "s3://$S3_BUCKET" --recursive
aws s3api delete-bucket --bucket "$S3_BUCKET" --region "$AWS_REGION"
```

Disable and remove the disposable R2 Data Catalog bucket:

```bash
curl --fail-with-body \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/r2-catalog/$R2_CATALOG_BUCKET/disable"

curl --fail-with-body \
  --request DELETE \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/r2/buckets/$R2_CATALOG_BUCKET"
```
