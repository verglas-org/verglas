Verglas uses one authorization system across lakehouses, Postgres databases,
Workers, Vessels, Integrations, Applications, queues, graphs, vectors, and
secrets. The tenant's authorization data is stored in the same Postgres service
as the scheduler, with separate schemas and database roles.

## Authorization model

Every authorization decision evaluates the current policy:

```text
tenant + principal + resource + action -> allow or deny
```

- A **principal** is a user, access token, service account, Agent turn, Job
  run, Vessel, Application, or Integration.
- A **resource** is a database or another protected object beneath it.
- An **action** is a specific operation such as `discover`, `query`, `append`,
  `execute`, `use_secret`, `deploy`, or `manage_grants`.
- A **grant** assigns actions to a principal on a resource.

The default is deny. An allow decision records the matching direct or inherited
grant and the policy version that was evaluated.

## Database resource hierarchy

The same hierarchy applies to managed and external lakehouses and to managed
Postgres databases:

```text
tenant
├── database:analytics                 lakehouse
│   ├── namespace:market_data
│   │   ├── table:trades
│   │   ├── graph:supply_chain
│   │   └── vector_index:documents
│   └── warehouse:analytics
├── database:operations                postgres
│   └── namespace:public
│       ├── table:customers
│       └── view:active_customers
├── job:market-ingest
├── vessel:shipping-dashboard
└── integration:market-data
```

A grant on a database is inherited by its namespaces, tables, vectors, graphs,
and views. Grant a child resource when a workload needs less access. For
example, an analyst can receive `query` for `database:analytics`, while an
ingestion Job receives only `append` for `table:trades`.

## Bootstrap the first owner

The self-hosted stack has no static administrative bearer token. Set these
values before the first `docker compose up`:

```bash
export VERGLAS_INITIAL_OWNER_EMAIL=you@example.com
export VERGLAS_TOKEN_SIGNING_KEY="$(openssl rand -base64 32)"
export VERGLAS_TARGET_JWT_SIGNING_KEY="$(openssl rand -base64 32)"
export VERGLAS_IDENTITY_ASSERTION_KEY="$(openssl rand -hex 32)"
```

The access service registers the email as the tenant's first owner only when
the tenant has no owner. After that, normal grants govern every user and
process. Changing the environment value does not transfer ownership. Rotate
ownership using the Access administration UI instead.

`VERGLAS_TOKEN_SIGNING_KEY` is the base64 encoding of exactly 32 random bytes
and signs access tokens. `VERGLAS_TARGET_JWT_SIGNING_KEY` is the base64
encoding of a separate raw 32-byte Ed25519 seed used to sign target JWTs for
database runtimes. `VERGLAS_IDENTITY_ASSERTION_KEY` is a separate 64-character
hexadecimal secret shared only by the Verglas OS identity broker and access
service to verify a short-lived signed login assertion. Keep all three values
in deployment secret storage. Do not pass them to a CLI, SDK, Worker, Vessel,
or Integration.

## Create a personal access token

Use **Profile → Access tokens** in Verglas OS:

1. Select **Create token**.
2. Give the token a recognizable name and expiration.
3. Select the databases or individual resources it needs.
4. Select only the required actions.
5. Copy the token when it is shown once and save it locally.

The token is a child principal of its creator. A user can delegate only actions
the user already holds. A token identifies its tenant, principal, audience,
issue time, expiration, and policy version. It does not embed a permanent copy
of permissions: each request evaluates current grants, so a revoked grant or
token takes effect immediately.

For a CLI token, use the initial token only to mint a narrower replacement. The
CLI writes that new token to an owner-only local credentials file and uses it
automatically for the same access endpoint:

```bash
export VERGLAS_ENDPOINT=http://127.0.0.1:8334
export VERGLAS_ACCESS_ENDPOINT=http://127.0.0.1:8345
export VERGLAS_TOKEN=TOKEN_SHOWN_ONCE

verglas token create local-cli \
  --grant database/analytics=discover,describe,query \
  --expires-in-seconds 2592000
unset VERGLAS_TOKEN

verglas query analytics 'SELECT 1 AS ready'
```

The CLI stores credentials in `~/.config/verglas/credentials.json` by default,
with owner-only permissions. Override that path with `VERGLAS_CREDENTIALS_FILE`
when a non-default secure location is required. Do not put a token in a command
argument, source file, Docker image, or repository. Revoke it from **Profile →
Access tokens** or `verglas token revoke TOKEN_ID` when a machine is lost, a
project ends, or its scope is no longer needed.

## Administer tenant access

Users who hold `manage_grants` can use **Admin → Access** to:

- View users, workload principals, databases, and their resource trees.
- Create, change, or revoke grants.
- Inspect effective access for one principal, resource, and action.
- View token identity, creation time, expiration, and last use.
- Revoke a user or workload token immediately.

The UI creates grants through delegated requests. It cannot grant an action the
approving user does not already possess. Agents request a permission widget;
they cannot silently expand their own or another principal's scope.

## Workload identities

The runtime creates a separate process principal for every Job run, Vessel,
Application, and Integration. It grants that principal only the declared
resources and actions, then issues a short-lived scoped token.

The server's background database-inventory synchronizer uses the same model.
The access service writes its rotating scoped credential to a private volume;
the server reads it through `VERGLAS_ACCESS_TOKEN_FILE` and never receives a
tenant-owner credential. Workload credentials must not be reused by an
interactive CLI or exposed through a UI.

Lakekeeper uses a separate read-only `policy-engine` credential file. Its
Verglas adapter evaluates each direct catalog request against the same tenant
policy rather than using Lakekeeper's permissive `allowall` backend. Catalog
requests carry the trusted database identity selected by the Verglas database
gateway, so each project and warehouse is evaluated beneath its own database
resource root.

## Secrets and Postgres credentials

Secret access is separate from data access. To let an Integration use an API
credential without exposing it:

1. Register the Integration as a principal.
2. Grant `use_secret` on the secret resource.
3. Grant `query`, `append`, or `execute` on the required data resources.
4. Let the trusted runtime resolve the secret only for that principal.

Applications and prompts never receive the secret value. For Postgres,
Verglas exchanges the authorized principal token for a short-lived,
database-restricted connection credential. It does not distribute the tenant's
Postgres administrator password.
