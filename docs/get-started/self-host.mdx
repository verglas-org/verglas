description: "Run one local Verglas cache against a managed Iceberg catalog."

The OSS distribution is one disposable `verglas-cache-node`. Production
control-plane services remain in Verglas Cloud. The node does not bootstrap an
object store or an Iceberg catalog; its provider owns catalog transactions and
table placement.

Every profile enables all local core surfaces:

- **Tables** use the cache-owned Iceberg REST gateway at
  `http://127.0.0.1:8334/catalog` and the cache S3 endpoint at
  `http://127.0.0.1:8333`.
- **Graphs** and **Vectors** use their signed APIs on the local S3 endpoint.
- Data files route through that local S3 endpoint, while the cache gateway owns
  provider catalog authentication. Clients never receive the provider catalog
  token or AWS signing credentials.

Set the local cache's own SigV4 keypair for every profile:

```bash
export VERGLAS_S3_ACCESS_KEY_ID=verglas-local
export VERGLAS_S3_SECRET_ACCESS_KEY='choose-a-local-secret'
```

Start the one-process deployment after choosing exactly one profile:

```bash
docker compose up --detach --build verglas
until curl --fail --silent http://127.0.0.1:8334/admin/healthz; do sleep 1; done
```

To run the released image instead of building from source, use
`ghcr.io/verglas-org/verglas-cache-node:latest` with the same environment
variables and ports.

Ports 8333 and 8334 are the defaults. Set `VERGLAS_S3_HOST_PORT` and
`VERGLAS_ADMIN_HOST_PORT` before Compose when those host ports are occupied;
client discovery advertises the selected mappings.

The cache state is only `./.verglas` by default. Delete it when the local node
is no longer needed:

```bash
docker compose down
rm -rf ./.verglas
```

## Verglas Cloud

This profile is the self-hosted edge/cache configuration for a Verglas Cloud
catalog and managed object endpoint. It is intentionally a wiring stub in OSS:
Cloud provisions the catalog, scoped storage credentials, and callback target.

```bash
export VERGLAS_PROVIDER=verglas-cloud
export VERGLAS_STORAGE_BUCKET=cloud-managed-bucket
export VERGLAS_STORAGE_ENDPOINT=https://s3.region.verglas.example
export VERGLAS_STORAGE_REGION=us-west-2
export VERGLAS_STORAGE_ACCESS_KEY_ID=...
export VERGLAS_STORAGE_SECRET_ACCESS_KEY=...
export VERGLAS_CATALOG_URI=https://catalog.region.verglas.example/iceberg
export VERGLAS_CATALOG_WAREHOUSE=cloud-warehouse
export VERGLAS_CATALOG_TOKEN=...
export VERGLAS_CATALOG_EVENT_TOKEN='shared-cache-callback-secret'
docker compose up --detach --build verglas
```

Cloud sends authenticated mutation hints to
`POST /admin/catalog/events`. Hints wake reconciliation early; they never
replace it. The cache always polls at
`VERGLAS_CATALOG_POLL_INTERVAL_SECONDS` (30 seconds by default), so a missed
event converges safely.

## Cloudflare R2 Data Catalog

Cloudflare R2 Data Catalog is the Iceberg REST catalog and controls where
tables live. Do not configure a `data_path` or create a second warehouse. Use
the catalog URI and warehouse Cloudflare provides, plus an R2 credential that
can read and write the catalog-managed bucket.

```bash
export VERGLAS_PROVIDER=cloudflare
export VERGLAS_STORAGE_BUCKET=r2-catalog-managed-bucket
export VERGLAS_STORAGE_ENDPOINT=https://ACCOUNT_ID.r2.cloudflarestorage.com
export VERGLAS_STORAGE_REGION=auto
export VERGLAS_STORAGE_ACCESS_KEY_ID=...
export VERGLAS_STORAGE_SECRET_ACCESS_KEY=...
export VERGLAS_CATALOG_URI='<Catalog URI printed by Cloudflare>'
export VERGLAS_CATALOG_WAREHOUSE='<Warehouse printed by Cloudflare>'
export VERGLAS_CATALOG_TOKEN=...
docker compose up --detach --build verglas
```

R2 Data Catalog has no cache callback contract in the OSS deployment. The
cache polls its catalog for committed changes. The catalog gateway retains the
R2 bearer credential in an owner-only file, and Graphs, Vectors, and Tables
all use the local gateway instead of connecting to Cloudflare directly.

## Amazon S3 Tables

Amazon S3 Tables is a catalog-managed provider: the table-bucket ARN is the
warehouse and its service chooses underlying table storage. Do not set a data
bucket. The cache accepts the dynamic `*--table-s3` table buckets through its
local S3 listener and signs both catalog and storage requests with the supplied
AWS credentials.

```bash
export VERGLAS_PROVIDER=aws-s3-tables
export VERGLAS_STORAGE_REGION=us-west-2
export VERGLAS_STORAGE_ACCESS_KEY_ID=...
export VERGLAS_STORAGE_SECRET_ACCESS_KEY=...
export VERGLAS_CATALOG_WAREHOUSE=arn:aws:s3tables:us-west-2:123456789012:bucket/example
docker compose up --detach --build verglas
```

The profile derives `https://s3tables.<region>.amazonaws.com/iceberg`; set
`VERGLAS_CATALOG_URI` only to override that standard endpoint. The S3 Tables
REST catalog uses SigV4 service name `s3tables`. Verglas polls it
for committed metadata changes; no event callback is assumed. The generated
configuration stores AWS credentials in owner-only files and never places them
in `config.toml`.

## Connect a client

Use `GET /admin/access` on port 8334 for client discovery. It advertises the
local `/catalog` Iceberg gateway for explicit table create/ensure. The current
SDK Table routes run on the same local admin listener:

- `POST /v1/ingest/{name}?mode=append&format=jsonl` appends rows.
- `GET /v1/tables/{name}/snapshot` reads the current snapshot.
- `GET /v1/tables/{name}/rows?limit&cursor` scans a bounded page.
- `GET /v1/tables/{name}/delta?since=&limit=` reads committed changes.

Configure Iceberg clients with the local S3 endpoint and the `VERGLAS_S3_*`
keypair above. Use the local signed semantic clients for Graphs and Vectors.
All client data-plane traffic then stays on the cache node before it reaches
provider-managed table storage.
