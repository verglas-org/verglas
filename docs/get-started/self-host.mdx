This guide starts a tenant-local Verglas stack with an empty provider registry.
Object stores, catalogs, and databases are added dynamically through the access
API. You do not put provider credentials in Compose or restart the cache when a
database is added.

The running application exposes:

| Port | Service | Used by |
| --- | --- | --- |
| `8333` | S3-compatible cache | Query engines and SDKs |
| `8334` | Query, write, catalog, and admin API | The `verglas` CLI and SDKs |
| `8345` | Tenant access API | Database and scoped-secret commands |
| `8360` | Local container runtime manager | Optional managed services |
| `8390` | Agent runtime | Verglas OS workspaces |
| `8787` | Verglas OS | Community and development UI |

## Before you begin

Install [Docker Desktop](https://docs.docker.com/desktop/) or Docker Engine
with Compose, Git, and the Rust toolchain.

<Steps>
  <Step title="Clone Verglas and install the CLI">
    ```bash
    git clone https://github.com/verglas-org/verglas.git
    cd verglas
    cargo install --path bins/verglas --locked --force
    verglas --version
    ```
  </Step>

  <Step title="Review the Compose bootstrap">
    The repository's `docker-compose.yml` is the source of truth for the
    complete OSS stack. It starts the data server, the scheduler and its
    Postgres queue, the trusted container-runtime manager, and Verglas OS. No
    profile or additional `verglas` command is required.

    Only the runtime manager receives the Docker socket. It owns dynamically
    generated Vessels and other optional containers on the fixed
    `verglas-runtime` network. The OS is a community and development surface;
    the server and CLI remain usable independently of it.
  </Step>

  <Step title="Start Verglas">
    Build and start the stack with no provider environment:

    ```bash
    docker compose up --detach --build
    ```

    Compose generates the tenant secret-encryption key once and retains it in
    the `verglas-secret-key` named volume. It is not a provider credential and
    is never embedded in the Compose file.

    Wait until the health endpoint reports `ready`, then connect the CLI:

    ```bash
    until curl --fail --silent http://127.0.0.1:8334/admin/healthz; do sleep 2; done
    export VERGLAS_ENDPOINT=http://127.0.0.1:8334
    export VERGLAS_ACCESS_ENDPOINT=http://127.0.0.1:8345
    export VERGLAS_TOKEN=verglas-local-access
    verglas status
    ```

    Open Verglas OS at `http://127.0.0.1:8787`.

    Confirm that the runtime manager can reach Docker:

    ```bash
    curl -i http://127.0.0.1:8360/health
    docker compose logs -f verglas-container-runtime
    ```

    If startup fails, read the server log:

    ```bash
    docker compose logs verglas-server
    ```
  </Step>
</Steps>

## Next: create a database

Create a managed lakehouse with `verglas db create analytics --type lakehouse`,
or create scoped S3 and Iceberg REST secrets before declaring a customer-owned
database. Provider values are prompted or read from stdin and never belong in
the process environment.

## Stop the cluster

```bash
docker compose down
```

This stops the stack. Dynamically managed containers retain their declared
state and are reconciled when the manager starts again. Named volumes retain
the cache, access/scheduler Postgres data, runtime state, OS state, and the
tenant secret-encryption key. Add `--volumes` only when you intentionally want
to delete all of that local state.
